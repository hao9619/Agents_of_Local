# Git 与多机接续工作规范

## 目标与适用范围

适用于用户以 GitHub 保存大项目、在多台电脑之间接续工作的场景，包括代码、论文、办公资料及混合研究项目。目标是：**每轮有实际成果或状态变化的工作结束时，代码、必要证据和最新进展已经保存在根仓库可收录的位置；用户可以直接在根目录暂存、提交和推送，无须再要求 Agent 整理一次。**

本规范与[文档管理规则](documentation.md)、[会话监管规则](codex-subagent-model-selection.md)配合使用。用户明确的任务范围、只读要求和发布权限优先。安装本规范不会自动建立仓库、改写 `.gitignore`、上传文件或调整现有仓库结构。

首次接入或规则变化时了解本规范；同一会话的后续轮次复用已确认信息，日常收尾执行第 7 节的增量检查。仅在涉及相应问题时回查忽略规则、第三方仓库、大型工件或多机冲突章节，不每轮全文重读。

## 1. 一个项目一个根仓库，一个主分支

- 以用户确定的大项目根目录作为 GitHub 同步仓库边界。先用 `git rev-parse --show-toplevel` 核对实际 Git 根；同名副本、Git 子仓库和根目录旁的工作文件不自动属于该仓库。
- GitHub 同步仓库只使用一个长期主分支。新仓库默认 `main`；已有仓库只有 `master` 时可继续沿用，不为统一名称擅自改名。默认也在本地主分支工作，不为临时任务创建功能分支、远端分支或新的 worktree。
- 一个主分支可以包含许多普通提交，不等于整段历史只能有一个提交。不得为了“单主分支”反复 amend、压缩或强推已同步历史。
- 已有其他分支、detached HEAD 或 worktree 时，先核对未同步成果及用户当前安排，不能直接删除、切换或强行归并。第三方官方 PR 仓库有独立流程时，明确区分其分支与个人 GitHub 同步仓库；不把官方单提交或 PR 分支要求套到所有项目。
- Agent 负责日常落盘、状态维护和检查。默认由用户执行 `git add`、`commit`、`push`，Agent 不擅自改变暂存区、远端、分支或发布状态；用户另有明确授权时按授权执行。

## 2. 开始工作时确定真正的工作位置

首次接入项目、换机或仓库结构变化时，核对以下信息并在现有入口中保留简短说明；普通轮次复用已有结论，不重新全盘调查：

| 信息 | 必须明确的内容 |
| --- | --- |
| 仓库边界 | Git 根目录、GitHub 同步目标、主分支；远端地址不能含凭据 |
| 当前工作树 | 本轮实际编辑和执行的代码目录，以及它如何进入根仓库 |
| 状态入口 | 一处稳定的当前状态文档和本任务证据入口 |
| 外部依赖 | 不在 Git 内的数据、权重、第三方源码及恢复位置 |
| 活动任务 | 当前负责人、其他会话的文件范围、远端仍在运行的任务及最近核验时间 |

开始实际修改前读本目录状态和相关任务记录；确认本机是否已接收上一台电脑的提交。未联网核对时只说本地已知状态，不把缓存的 `origin/main` 当作远端此刻的状态。

## 3. 根目录 `.gitignore` 管理收录范围

根目录 `.gitignore` 是本项目主要的、随仓库共享的收录约定，须由根仓库跟踪。优先排除明确的可重建产物和本机私有数据，让新的代码、脚本、配置和文档自然进入 Git 的候选范围。

- 通常保留：实际源码、测试、运行脚本、依赖与环境声明、不含秘密的配置示例、README、AGENTS、项目协作规则、当前状态、必要的小型结果与复现证据、采用的论文或办公交付件。
- 通常排除：虚拟环境、缓存、构建输出、临时下载、重复备份、凭据、本机认证与会话状态、大型原始数据和权重。具体文件按用途判断，不能把所有日志、JSON、ZIP、PDF 或模型扩展名一律视为可丢弃。
- 不用 `/docs/*` 加几个历史日期文件的放行规则管理持续发展的文档目录。已有白名单项目应建立稳定的源码、状态、证据入口，并保证新一轮文件也能收录；不得每次写完新报告才等待用户发现遗漏。
- 不把源码、实验脚本、唯一进度记录或唯一必要证据仅放在 `runs/`、`artifacts/`、`backup/`、`.tmp/`、`.codex/` 等被忽略的位置。确有临时计算需要时，在形成结果的同一步写出可收录的正式文件或必要摘要。
- `.agents/` 中可共享的项目规则、安装工具和清单应检查是否被跟踪；不能因本机助手状态需要排除就屏蔽所有协作规则。机器专用状态单独存放。
- 子目录原有 `.gitignore`、`.git/info/exclude` 和全局 `core.excludesFile` 也可能影响收录。保留有用途的既有规则，定位具体匹配来源；不为“根目录统一管理”直接删除第三方规则或改全局配置。[Git 忽略规则说明](https://git-scm.com/docs/gitignore)
- `!文件` 不能直接救回已被排除父目录中的文件，需要检查父目录是否也已放行。已跟踪文件不会因为新增忽略规则就退出索引；历史中的文件也不会因此消失。修复要区分新增文件、已暂存文件和历史对象，不能默认执行全仓 `git rm --cached` 或强制添加。[Git 忽略规则说明](https://git-scm.com/docs/gitignore)
- `.gitignore` 不按大小动态过滤文件，也不检查内容是否含秘密。新增大文件、配置和日志时检查其实际大小与内容；不能只凭扩展名或“已忽略”标签判断。

修改忽略规则后，用本轮应收录和应排除的代表文件分别核查。具备修改权限时在当前工作中修复明确误屏蔽；无权改根目录时给出具体规则和受影响路径，不越界修改，也不宣称已经可同步。

## 4. 代码不能只留在嵌套仓库或旧副本里

优先直接在根仓库跟踪的正式源码目录开发。一个 GitHub 根仓库可以包含多个普通源码子目录，不必让每个子项目都拥有自己的 `.git`。

### 第三方仓库的归属和来源

- 用户选定的默认方式是**直接将第三方源码作为普通目录收录到大项目根仓库**，保留来源和归属；需要更新时再从原上游取得源码。默认不使用 submodule，也不要求保留该目录独立的 Git 关联。
- 收录他人仓库时，保留原作者、组织、仓库名、原始许可证及版权声明。保留代码、安装脚本、子模块声明和依赖配置指向的真实上游地址，不改为用户自己的用户名、仓库或个人 Fork，不把收录描述为原创。
- 使用已有来源说明，或在收录目录边上增加简短来源记录，注明原所有者、上游 URL、固定提交或版本、取得日期、许可证位置及本地修改范围。地址不含令牌；缺失的信息标为待核对。
- 不为纳入根仓库随意删除第三方文件。新收录的普通源码副本排除 `.git` 元数据；`.gitignore`、`.gitattributes`、`.gitmodules`、许可证和依赖文件仍按原用途保留，并检查是否影响根仓库收录或后续构建。原有独立检出的历史和未提交成果先保全，不能为方便收录直接丢弃。
- 删除 `.git` 会移除该目录独立的本地历史和 remote 配置，保留上游链接不能代替独立的 Git 关联。`.git` 也可能是指向共享元数据的文件，处理时不能沿其路径删除其他仓库的 Git 数据。
- 上游更新时，按已记录的原所有者和地址取得指定版本，审查与本地修改的差异后更新正式源码目录，并同步来源版本记录。不会因为上游有新提交就自动覆盖本地代码或替换依赖来源。

### 源码收录与同步

- 添加带 `.git` 的目录可能只记录 `160000` 类型的 gitlink，而非目录内的源码。父仓库状态干净不证明子仓库的未提交修改或未跟踪文件已经保存；只忽略 `**/.git` 也不能保证已嵌入仓库变成普通目录。[Git add 的嵌入仓库说明](https://git-scm.com/docs/git-add)
- 新建源码布局时，优先采用普通目录或明确的源码快照。既有独立仓库不能直接删 `.git` 来扁平化，先保留其历史、未提交修改及必要远端关系，再确定迁移方案。
- 如果必须在独立的官方贡献检出中开发，明确唯一开发来源、根仓库中的同步目标和路径映射。建立可重复的增量同步方式，并在形成改动的日常步骤同步，而非推送前临时复制整个工程。新增文件、必要依赖和经确认的删除也要对应处理；目标有他人改动时先协调，不能用无差别删除式同步覆盖它。
- 快照记录来源仓库、基线提交，以及是否包含未提交修改。只记 HEAD 不足以描述修改后的工作树；必要时记录本轮文件清单或内容哈希。每次结束核对实际修改文件与快照的一致性，不默认对全部旧文件重新哈希。
- 用户要求直接包含的第三方仓库必须收录实际源码，不能只留下 URL、提交号或恢复说明。另行明确为外部下载项的依赖可记录来源、固定版本及恢复方法；自己的改动必须保存为根仓库中的源码或可验证补丁，不能仅留下一个指向上游旧版本的链接。
- 采用完整源码快照时，核对嵌套依赖目录是否有实际源码，不能把尚未初始化的空子模块或 LFS 指针称为完整内容。保留原依赖声明，说明哪些依赖已直接收录、哪些仍需按原上游地址恢复；不要假定删除 `.git` 后原来的子模块更新命令仍可直接使用。
- submodule 仅在用户接受其额外恢复流程时采用，须有可用的 `.gitmodules`、可访问的固定提交和子仓库成果。普通父仓库 push 不会自动发布子仓库提交；不把 submodule 当作“根目录一次 push 保存一切”的默认方案。
- 符号链接只记录链接目标，不自动保存目标内容。跨仓库、跨磁盘或指向个人绝对路径的必要文件要有明确的收录或恢复安排。

## 5. 工作过程中持续写入进展

- 产生有效代码改动、实验结果、关键决定、阻塞或下一步变化时，更新已有的主要状态入口。完成一轮实质工作、暂停交接或结束前，状态必须与已落盘的成果一致；不能只在聊天里汇报“完成”。
- 状态入口使用稳定路径，例如已有 README 状态区、`docs/status.md` 或 `项目状态.md`。正文开头保留一份当前总结；旧状态移到明确的历史区域或任务记录，不不断叠加多份相互矛盾的“当前状态”。
- 当前总结简短记录：更新时间和时区、目标、正在采用的源码位置与版本、完成及未完成事项、已验证范围、阻塞、下一步、证据入口、活动任务与负责会话。纯讨论且未形成新决定、无实质变化的查询，无须制造进度提交。
- 子项目维护自己的详细状态；父目录主要维护导航和必要摘要。父级内容过期时，在权限范围内更新直接受影响的摘要；无权更新则在交接记录中明确待同步项。
- 进展与 Git 发布状态分开：工作已落盘、可暂存、已提交、已推送、远端核对过是不同状态。Agent 未执行提交推送时应如实写“未由 Agent 提交或推送”，不能推断用户没有在其他终端操作。
- 本轮失败、尚未完成或验证不足也可以形成真实的接续记录。不得为了让状态好看而虚构完成，也不为更新记录重跑已经充分验证的实验。

## 6. 大型工件与远端任务的接续

Git 中至少保留足以理解和核对结论的轻量信息：源码或版本依据、配置、非敏感命令、关键指标、必要的小型原始证据、退出状态和外部工件索引。完整大型原件按项目约定另行保存。

- 外部工件索引沿用已有 `ARTIFACTS.md`、数据说明或状态文档；按需要记用途、版本、大小、哈希、非敏感的持久位置、恢复步骤、所需权限以及最近恢复核验结果。
- 区分“本机存在”“远端存在”“已复制”“已核验可恢复”“尚未转移”。有文件名或 SHA256 不等于文件已经备份；只有本机绝对路径也不能称另一台电脑可恢复。
- 新结果形成时同时生成轻量指标和必要证据到可跟踪目录。被忽略的原始日志中若有唯一失败原因或复现实验所需数据，应保存经过检查的必要片段或独立证据文件，不能只留下一个克隆后失效的链接。
- 新电脑读取已有数值，与从 checkpoint 继续训练、重新取得输入图片，是不同能力。说明本仓克隆后可以做什么、还缺什么；缺失原图或权重时不声称已完成全部备份。
- 模型权重、数据集、视频和大型运行包按需要采用 Git LFS 或独立工件存储。LFS 需要在各台电脑配置、上传对象并验证实际下载；提交了指针并不代表对象已可恢复。采用方案须符合已有存储和费用授权。
- 截至 2026-11-03，GitHub 普通 Git 对超过 50 MiB 的文件给出提示，阻止超过 100 MiB 的文件。首次迁移还要考虑历史对象；仅从当前目录删除大文件或加入 `.gitignore` 不会清掉待推送历史。遇到历史迁移需求单独处理，不自动重写历史。[GitHub 大文件说明](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)
- 远端作业仍在运行时，提交一次状态不会自动同步未来结果。记录项目/任务标识、非敏感主机别名、工作目录、最近实际观测时间、日志位置和状态检查/停止方法。新会话先核对原任务，不重复启动；结果由当前负责会话在收集时增量写入仓库。
- PID、会话 ID、SSH 连接、凭据与硬件环境不会随 Git 克隆恢复。必要连接与解密密钥通过已授权的独立渠道迁移，不写入 Git；未转移时明确列为接续缺口。

## 7. 每轮结束前做轻量增量检查

以下检查属于本轮工作的一部分，由 Agent 主动完成。主要针对本轮修改、新增、移动、删除的文件，以及被直接影响的入口和规则；无需用户再下“整理项目”的指令。

1. **落盘：**本轮成果在正确的工作树，状态入口已更新，来源与快照已按约定同步。
2. **收录：**从根仓库确认本轮必需文件已跟踪或会作为普通文件被识别，不是被忽略、位于仓库外或仅成为子仓库指针。
3. **依赖：**检查新改入口的相对路径及必要资源；外部工件有真实恢复位置或明确缺口。
4. **内容：**检查本轮新增/改变文件是否含凭据、意外大文件、无关副本或他人正在产生的输出；不能依赖 `.gitignore` 自动发现这些问题。
5. **验证：**复用本轮已有测试与证据，完成必要的差异检查；区分未暂存和用户已暂存的版本。若用户在 Agent 完成后又改文件，需重新暂存相应变更。

常用只读命令如下；在实际仓库根执行，示例路径替换为本轮文件：

```bash
git rev-parse --show-toplevel
git branch --show-current
git status --short
git status --short --untracked-files=all -- "本轮修改的目录或文件"
git ls-files --stage -- "本轮必需文件或源码目录"
git check-ignore -v --no-index -- "本轮必需文件"
git diff --check
git diff --cached --check
```

`check-ignore --no-index` 用来诊断规则，不能单独判断跟踪状态；其输出中 `!` 开头的匹配表示放行。结合 `ls-files` 和 `status` 判断，没有输出或没有差异都不能单独证明文件已在 GitHub。`git diff` 默认也不展示未跟踪新文件的内容，新增文件需要直接查看。[Git check-ignore 说明](https://git-scm.com/docs/git-check-ignore)

只在首次接入、忽略规则或仓库布局改变、发现具体遗漏时扩大检查。不要每轮全库扫描全部历史、重打包 GB 级产物、重新复制整套源码、重新克隆验证或新增长篇报告。有现成检查脚本时复用；持续有重复步骤时，可在授权范围内将其固化为小型增量检查工具，而不是增加模型反复阅读。

最终回复简要说明：本轮代码/文档位置、状态入口、检查结果、未包含的必要工件和 Git 操作是否已执行。存在遗漏时说清具体阻塞；符合条件时可说“本轮成果已落盘并检查可纳入根仓库，待用户暂存、提交和推送”。这不保证网络、认证或远端状态不会变化。

## 8. 单主分支下的多机与多会话协作

- 默认按机器交接：A 机完成本轮并成功推送，B 机取得该提交后再继续修改同一项目。若必须同时在多机工作，先分配不重叠文件和一个集成人；单主分支本身不会解决并发冲突。
- 同一工作树内多个会话共享文件与索引。指定一个 Git 操作负责人；辅助会话不自行暂存、提交、切换分支或拉取。用户执行根目录 `git add -A` 前，相关写入应到达一致的阶段边界，避免把另一会话的半成品一起收录；无关远端实验无需因此停止。
- 新机器先核对工作树、主分支和本机未推送提交，再执行同步。工作树有未提交改动时先保全和审查；不自动 stash、reset、clean 或整文件选择 ours/theirs。
- 推荐用显式的 `git pull --ff-only` 接收更新；发现双方独立提交时会停止，保留两边成果并检查差异，再决定合并或对未发布本地提交重放。合并提交不增加第二个长期分支。不得为维持单分支外观强推覆盖另一台电脑的工作。[Git pull 说明](https://git-scm.com/docs/git-pull)
- 推送遭拒时先看是否远端已前进或认证失败，不盲目反复 push，不默认 `--force`、`--force-with-lease` 或 `--mirror`。已经推送共享的历史保持稳定。[Git push 说明](https://git-scm.com/docs/git-push)
- 持久路径优先相对项目根解析；数据根、设备和本机目录通过配置或环境变量指定。已有环境文件保留依赖版本，不把个人环境的绝对 `prefix` 当作所有电脑通用位置。
- Windows/Linux 混用时，新增路径避免仅大小写不同的同名文件、系统保留名及不可移植字符。脚本换行和可执行位按项目需要用 `.gitattributes` 等明确约定；不为本轮小修改全库转换换行或修改全局 Git 配置。

### 用户日常命令示例

前提：在正确根仓库的主分支，远端已配置好；下面以 `origin/main` 为例，现有主分支为 `master` 时替换名称。每步检查结果，有错误或意外文件即停止。

```bash
# 换机开始：先确认本机无待保全的修改或未同步成果
git status --short
git branch --show-current
git pull --ff-only origin main

# Agent 完成本轮，且其他会话已协调好写入范围后
git add -A
git diff --cached --check
git diff --cached --stat
# 审查暂存内容；没有应提交的差异时无需创建空提交
git commit -m "说明本轮修改"
git push origin main
```

`git add -A` 暂存新增、修改和删除，`commit` 才生成提交，`push` 发送提交。只执行 add 后直接 push，不会上传尚未提交的改动。[Git add](https://git-scm.com/docs/git-add)、[Git push](https://git-scm.com/docs/git-push)

这些命令由用户执行；本规范没有自动授权 Agent 推送或接管其他会话的工作。

## 9. “没有变化”时按具体状态排查

| 现象 | 优先核对 |
| --- | --- |
| `git add` 没输出 | 正常成功时可能无输出；查看暂存差异，不把静默当作失败 |
| `nothing to commit` 或根目录状态干净 | 修改是否保存到磁盘；是否在别的副本、仓库外、被忽略目录或子仓库；是否已提交；是否只有聊天记录变化 |
| push 显示 `Everything up-to-date` | 本轮是否 commit；推送的远端和分支是否正确；不要把“无新提交可推送”当成文件已同步 |
| 父仓库仅显示目录或 gitlink | 核对 `160000` 条目、子仓库未提交改动和 `.gitmodules`，确认实际内容的保存方式 |
| 新报告看不见、旧报告能提交 | 查日期白名单、被排除的父目录及更深层忽略规则 |
| 本地有文件，另一台电脑没有 | 核对该路径是否进入提交、该提交是否成功推到目标分支，以及新电脑是否取得它；再查 LFS、子模块与外部工件 |
| 明明改了已跟踪文件，却无差异 | 定向检查实际字节、错误工作树、稀疏检出及 `assume-unchanged`/`skip-worktree` 等特殊索引状态，不盲目重建整个索引 |

不要通过创建无意义文件或只改时间戳，让 Git “看起来有变化”；应找到真实成果所在的位置。
