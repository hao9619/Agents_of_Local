# 文档编写与维护规范

本文规定项目文档的分类、信息归属、维护责任、阅读范围和写作要求。适用于项目内自行维护的 Markdown 文档，包括 AGENTS.md、README.md、开发指南、设计、调研、规格、计划、审阅和报告。

目录组织规则同时适用于办公与研究资料工作区，包括 Word、Excel、PPT、PDF 和相关附件；具体文件格式与交付要求沿用各项目约定。

用户本次要求和明确的操作范围优先；目录与文件命名优先沿用项目已有约定。引用的上游文档、原始论文、日志和第三方材料保留原貌，不为符合本文而批量改名、迁移或改写。文档维护不自动授权修改范围外文件、启动实验或对外发布。

## 目录命名与结构

按工作区的主要用途选择结构：办公与研究资料以用途分类，代码项目以工程职责组织，混合项目在相应子目录内分别采用适合的结构。不能仅按文件扩展名判断，例如代码仓库中的 Markdown 使用说明仍属于工程文档。

### 办公与研究资料：数字前缀加中文用途

- 新建或获准整理的资料工作区，一级分类目录默认使用“唯一两位数字＋中文用途”，例如 `01组会材料`、`02论文原文`、`03论文复现`，便于排序、定位和输入前缀后补全路径。
- 分类按实际业务选择。办公项目可用需求资料、会议纪要、方案报告、交付材料等；研究项目可用组会材料、论文原文、论文复现、自主研究等。不机械复制其他项目的分类。
- 同一层级的分类数字不重复，可以留出编号间隔；例如 `10自主研究`、`90参考资料`、`99杂项`。编号用于分类与排序，不表示时间或完成进度，不能代替阶段性记录的日期。
- 编号确定后保持稳定，新增分类使用空闲编号，不为连续排序反复重命名已有目录。`99杂项` 仅用于暂未明确归属的材料，明确用途后归入对应分类。
- 下一层按任务、主题或论文组织；会议、周报和阶段交付使用 `YYYY-MM-DD` 或 `YYYY-MM-DD-主题`。无需给每层目录和每个文件都加数字前缀，也不按 PDF、PPT、Word 分散同一任务的配套材料。
- 根目录保留导航与协作规则；具体资料进入所属分类。同一任务的正文、附件、讲稿等放在一起，旧版本按项目约定归档，并标明当前采用版本。

研究资料结构示例，目录按需创建：

```text
研究工作区/
├── AGENTS.md
├── README.md
├── 01组会材料/
│   └── 2026-10-29-论文汇报/
│       ├── README.md
│       ├── 汇报_v2.pptx
│       ├── 讲稿_v2.md
│       └── archive/
├── 02论文原文/
│   └── 年份_会议_论文简称/
├── 03论文复现/
│   └── 年份_会议_论文简称/  # 内部沿用代码项目结构
├── 10自主研究/
├── 90参考资料/
└── 99杂项/
```

### 代码项目：沿用工程惯例

- 优先遵循现有仓库、框架与构建工具的目录约定，例如 `src/`、`tests/`、`docs/`、`scripts/`、`configs/`。保留工具要求的文件与目录名称，不给这些工程入口统一添加数字前缀。
- 工程文档放在已有文档目录，持续维护的说明使用稳定路径，单次任务记录使用带日期的文件或目录。源码、测试、配置、原始运行结果和交付产物按各自职责存放。
- 新项目可参考下列结构；不要求已有项目为此搬迁，也不要求小任务创建完整的计划、进度和报告文件。

```text
代码项目/
├── AGENTS.md
├── README.md
├── src/
├── tests/
├── scripts/
└── docs/
    ├── status.md
    ├── usage.md
    ├── design.md
    └── tasks/
        └── 2026-10-29-任务主题/
            ├── plan.md
            ├── progress.md
            ├── report.md
            └── evidence/
```

### 混合项目与已有目录

资料工作区可以用 `03论文复现/` 等分类收纳代码项目，各代码项目内部保持工程结构。代码仓库也可以在已有资料目录中用数字前缀整理办公材料，不改变源码与构建入口。跨目录的资料和结果通过索引链接关联，避免为适配两种结构复制出多套独立维护的内容。

上述规则用于新建内容及已授权的整理。处理已有目录时先核对引用、脚本路径和用户习惯；改名或迁移须在本次范围内保留原有材料并修复受影响路径，不因采用新规范自动整理其他项目。

## 文档分类与日期命名

| 类型 | 维护责任 | 日期标识 |
| --- | --- | --- |
| 持续维护文档 | 随代码、资源、已确认规则或当前状态持续更新 | 使用稳定路径，例如 `README.md`、`status.md` |
| 阶段性文档 | 对特定任务、阶段或代码基线负责，不承诺随后续代码持续更新 | 文件名或所属任务目录名包含精确到日的 `YYYY-MM-DD` |

- 新建文档先确定维护责任。采用本文默认命名时，持续维护文档使用稳定路径，阶段性文档使用路径日期；正文中的更新时间不能代替阶段性文档的路径日期。
- 独立的阶段性文档使用 `YYYY-MM-DD-<topic>.md`。同一任务的阶段性文件可以放在含日期的任务专属目录中，内部使用 `progress.md` 等固定文件名，例如 `.superpowers/sdd/2026-10-24-example/progress.md`；引用和交付时保留含日期的任务路径。
- 面向一次任务的调研、规格、实施计划、审阅、执行记录和问题报告属于阶段性文档；持续描述现行接口或产品要求的规格可以作为持续维护文档。按实际职责分类，不只看标题。
- 路径日期表示任务或记录形成的日期，普通修订不反复更名；同日不同任务用主题区分。任务日期、记录日期和实际验证时间不一致时分别说明，不猜测未知日期。
- 带日期不表示文档已经失效。本次正在实施的规格和计划仍是本次任务的依据；任务结束后，它们不再承担当前行为说明的责任。
- 持续维护文档可以记录已实现行为、已确认但尚未实现的要求和开放问题，但必须明确区分。
- 已有文档先核对用途、适用版本和引用关系，不能仅凭文件名没有日期就认定它代表当前状态。遇到命名不清的历史记录，先补充性质与基线说明；需要改名或迁移时，在授权范围内同步修复引用，不为统一格式开展全库整理。

## 文档职责与唯一来源

- 每项需要持续维护的规则、接口或状态指定一个主要维护位置，其他文档通过链接引用。允许必要摘要，但摘要应与来源一致，不在多处独立维护完整副本。
- 先查已有入口和记录再新建文件；一份文档可以承担多个相近职责。下面的位置是职责示例，不要求每个项目创建一整套文件。
- 上层文档主要提供导航和稳定背景。具体项目的状态优先维护在该项目入口或指定状态文档；上层若保留进度摘要，状态变化时同步更新。
- 当前用户要求、任务书、接口契约、代码、测试和历史报告承担不同职责：要求说明应当怎样，代码与运行证据说明实际怎样。发现冲突时核对适用范围、版本与最新决定，不按文件名、修改时间或单一来源直接裁定。
- 原始证据保留在明确位置，报告引用证据并说明结论；同一结论的 Markdown、表格、幻灯片等交付版本应标明共同来源，避免各自维护不同数字。

### 按信息职责选择位置

| 信息职责 | 推荐维护位置与边界 |
| --- | --- |
| 长期协作规则 | 适用范围内的 AGENTS.md；记录操作边界、约定和必要入口，具体环境、临时进度与实验结果放到项目记录。子目录仅补充差异，避免复制整份上级规则 |
| 项目入口与使用方法 | README.md 或使用指南；说明用途、必要操作和当前状态入口，避免堆入全部实验历史 |
| 当前状态与交接 | 已有 README 的状态区或独立状态文档；记录当前采用版本、完成范围、阻塞、下一步和证据入口，选择一处作为主要维护位置 |
| 需求、接口与设计 | 对应规格或设计文档；区分已确认要求、当前实现、候选方案和待决定事项，写明适用版本 |
| 单次任务与实验 | 带日期的任务目录或报告；记录目标、方法、基线、配置、结果、失败方案及结论，不承担后续所有版本的状态维护 |
| 原始证据与交付件 | 项目已有的 reports、docs、runs 或交付目录；保留日志、数据、源码或产物定位和校验信息，索引指向当前采用或已提交的版本 |

可复用提示词保留通用规则，将工作目录、设备、当前状态和权限作为本次任务输入。不能把某次服务器授权、通过结论或项目专有验收要求写成其他项目的默认事实。

## 多层项目的安装与会话交接

### 根目录安装，子目录按需配置

用户先在大项目根目录完整安装一次。安装结果包含四份规则及 `install_agent_docs.py`，后续 Codex 可使用安装后的工具配置子目录，无须用户逐个复制源文件。根目录采用本规则后，允许在本轮已经授权写入的范围内按需配置；更严格的只读要求、目录边界和项目约定优先。

- 触发时机：实际进入某个子目录开展工作、准备交接给该目录主会话，或发现已有入口缺失、失效时。仅浏览文件、列目录或读取历史不触发安装。不递归扫描并安装所有后代目录，不为尚未开展的项目预建会话或状态记录。
- 安装前先读目标目录现有 `AGENTS.md`、`AGENTS.override.md` 和状态入口，核对其他会话的写入责任。在用户可见的进度说明中交代目标目录和安装方式，已有按需配置授权无需每次再确认；目标不在本轮可写范围时只报告所需操作。
- 工具在指定根目录以内选择最近的已完整安装祖先作为规则来源。同一 Git 仓库且目标没有本地技能时，只写引用公共文档的入口及安装清单，不复制四份规则。独立 Git 仓库、未找到 Git 边界或目标已有本地技能时，在目标目录完整安装，以便该目录独立启动和发现技能。它只根据祖先 `.git` 标记判断；使用自定义项目根或技能发现配置时须结合实际加载情况核对。
- 调用根目录安装结果中的工具，传入 `--workspace` 和 `--project`，先预览再执行。目标必须是指定根目录内已存在的子目录，不能通过链接越界。已有受管内容被手改时停止覆盖，先核对冲突；不得自动追加 `--overwrite`。
- 引用模式随公共文档更新而使用新内容；完整副本由 Codex 在后续进入该目录时按需更新，不后台同步所有子项目。已有本地约定保留，根目录升级不代表所有本地副本已升级。目录搬迁后检查引用；需要独立搬走的项目先完整安装，避免保留失效的父目录引用。

示例命令中的路径须替换为实际路径；执行者须正确处理空格和特殊字符：

```bash
python3 "/大项目/.agents/skills/background-subagent/install_agent_docs.py" \
  --workspace "/大项目" --project "/大项目/子目录" --dry-run
# 确认预览仅涉及本轮可写目录、没有覆盖冲突后，去掉 --dry-run 执行。
```

**启动前提：** 未配置的独立目录会话可能无法发现父目录规则，不能依靠它自行知道要安装。根目录或其他已经读到本规则的会话应先补齐目标入口，再由用户创建该目录主会话；已打开的会话应明确重新读取入口，技能列表未更新时重新启动。普通仓库内的子目录可继承规则，但不会因此自动创建会话或同步其他会话的记忆。

### 会话职责、记录位置与读写时机

通过 GitHub 在多机之间接续的项目，同时遵循 [Git 与多机接续规范](git-multicomputer-workflow.md)：代码、必要证据和当前进展须在日常工作中保存到根仓库可收录的位置，并在每轮实质工作结束前核对本轮增量。不能仅因文档在本机存在就认定换机后可读取，也不把同步准备留到用户要求推送时再做。

- 长期主会话由用户创建、指定职责并监管；辅助会话的创建与监管遵循[子代理规则](codex-subagent-model-selection.md)。每个实际管理的目录在自己的入口中说明职责范围、父子项目的关联及状态文档位置；会话身份、任务进度和监管决定放在状态记录，不把所有启动者都写成主会话。
- 优先沿用 README 的状态区或已有 `status.md`，缺少且确需交接时再创建一个稳定入口，如 `项目状态.md`。不另造多份相同进度台账。单次任务的详细交接与证据可放在带日期的任务目录，由稳定入口链接。
- 开始或恢复工作时，先读适用规则和本目录状态，核对用户最新要求、会话职责、活动任务、资源及文件负责人。只按任务需要读直属子项目的状态，不把上层摘要当作底层最新事实，也不默认通读全部子孙项目历史。
- 交接记录至少包含：目录及职责；主会话和相关辅助会话的实际标识（未知则标明）；监管者及已确认决定、时间和范围；目标、完成条件、读写边界及共享文件负责人；当前版本、已完成及未完成事项、证据与失败方案；运行中代理或进程的定位与停止方法；阻塞、待决定事项、下一步和更新时间。无关项可省略，不伪造会话 ID 或已获授权。
- 在派发和交接前、关键决定或范围变化后、阶段完成、受阻、暂停及结束时更新记录。接手者先核对已有运行任务，再继续执行；过期的 `running` 标签不能证明仍在运行，也不能据此启动副本。
- 本目录主会话维护主要状态；辅助会话写各自分配的任务记录，由主会话汇总。父目录主会话维护导航和必要摘要，链接到子项目状态。其他会话需要修改同一共享文件时先协调负责人，不并发覆盖，不因“父级协调”就擅自搬迁活动项目或改写其内部结论。
- 子目录变更需要父目录同步但当前无权写父目录时，在本目录交接中写明待同步项和来源；由父目录主会话下次读取时更新，不越界写入，也不承诺自动通知或立即同步。

## 文档与实现冲突

发现当前说明与代码、资源或运行证据冲突时，先区分“应有要求”和“实际行为”，再处理差异。

1. 核对适用版本、用户最新要求、相关代码或资源及已有测试证据。文档写着“通过”不能代替对应版本的验证记录；源码检查也不能自动证明实机行为。
2. 确认仅是当前说明过时时，在授权范围内修正该说明及受影响的摘要、示例和链接，并告知用户具体差异。纯文字或链接修正无须单独建立问题报告。
3. 已确认要求仍有效、实现尚未满足时，保留原要求，另写明实际行为、缺口及处理状态。不得通过修改文档、测试判据或验收范围，把实现缺陷改写为符合要求。
4. 判断不清时明确标为待核实，记录已有证据和具体疑点。涉及行为缺陷、验收差异或后续跟进的问题，应保留问题记录；即使本轮已修复，也记录处理和验证结果。修改文档本身不代表实现问题已解决。
5. 向用户说明影响结论或后续操作的差异、处理及遗留项，并提供相关记录路径。超出本次修改范围时只报告发现和建议，不自行修复范围外文件。

问题记录优先补充到已有任务报告、问题清单或规格中，只有需要独立跟踪时才新建。至少记录：

- 涉及的文档、代码、资源和核对基线；
- 原有描述或要求，以及核实到的实际行为；
- 判断依据、可能影响和仍需确认的问题；
- 已采取的修改、验证结果及当前处理状态。

记录位置优先沿用项目约定。仅供本轮排查的临时记录可放在 `.tmp/YYYY-MM-DD-<topic>-report.md`，但目录名称不等于已被 Git 忽略，应核对实际配置。需要交接或长期保留的问题与证据放入项目的持久记录位置，并从当前状态入口链接；不让未解决问题只留在临时目录。

## 历史文档的阅读范围

- 先读适用规则、当前状态入口和本次任务依据，再按具体问题查阅相关历史记录，避免从全部旧报告开始通读。
- 调研、计划和实现阶段均可定向查阅必要历史资料；本次规格未引用但确实相关的失败记录、决策或证据，不因缺少引用而禁止阅读。说明要解决的问题，核对适用性后补充当前依据，无须仅因查阅历史而暂停等待确认。
- 历史结论应结合当前代码、资源和版本核对；日期较早不表示无用，日期较新也不保证结论适用于当前任务。
- 本次规格和计划应写全实施所需的最终决定，或明确引用必要资料，不能依赖读者重读完整对话或自行猜测多个旧版本的取舍。
- 已完成任务的报告和已提交材料保留当时基线与结论。后续成果写入新记录或当前状态入口，不把历史报告整体改写为当前结果。发现原记录错误时保留可追溯的勘误，说明影响；已提交材料修订另存版本。

## 初见者有效信息

文档必须让首次阅读者理解适用范围、当前结论、执行要求和必要理由，无须了解此前对话、作者的思考过程或版本之间的修改经过。本原则适用于持续维护文档，也适用于阶段性规格、计划等文档。

- 当前说明中删除不影响理解或执行的讨论过程、提议者身份和修订流水。例如，最终要求直接写“值为 18”，不写“最初为 15，后来用户要求改为 18”。规格和计划在实施期间发生修订时，更新要求及受影响步骤；确需保留的旧决定移入历史记录，不让互相矛盾的指令同时生效。
- 保留会影响实施和维护的决策依据、限制、取舍与后果，并放在对应规则或设计附近。必要的失败方案及放弃理由属于有效信息，可用于避免重复试错。
- 审阅、审计、问题报告中的复现条件、核对基线、差异和验证证据属于有效信息；用明确的检查结论组织内容，不复述无关对话。
- 未实现的候选应写明候选内容、依赖、限制和待决定事项，不用“用户觉得不错，先记录”等措辞代替设计信息。
- 项目专有名词必须先核对正式名称，使用资源定义或所属持续维护文档中的名称；不得自行创造简称或别称。已确认的正式简称确需使用时，先给出与完整名称的对应关系。此要求同时适用于文档和对用户的说明。
- 示例、预期结果和实际观测分别标明；用“未测试”“运行中”“待确认”等准确状态，不用零值、空白或笼统“已完成”代替未知信息。

## 进度文档

包含任务勾选、任务表或其他实施进度记录的文档，必须在同一文档开头保留总结性进度说明，不能只提供分散的任务状态或让读者转到另一份文件判断整体进度。

此要求同时适用于含任务进度的计划和 `progress.md` 等执行记录，不因文件被 Git 忽略而免除。不记录实施进度的规格、调研或审阅文档，无须复制任务进度总结。

总结至少说明本轮目标、总体状态、已完成和剩余范围、当前步骤及阻塞情况；有明确任务总数时，同时注明完成数与总数。活动任务写明更新时间；涉及实验或交付时注明当前版本或对应记录。例如：

> 更新时间：2026-10-29。本轮目标：完成存档迁移及校验。当前状态：实施中。共 6 项，已完成文件迁移、索引更新等 4 项；正在进行存档校验，之后完成最终验证。暂无阻塞。

- 任务状态变化、暂停交接和完成时，同步更新总结与明细。
- 完成以用户本轮要求为准。仅要求小样本流程时，完成后不因未做全量实验而记为未完成；同时明确结果不能代表全量复现。
- 分别标明实现、验证、CI、提交、评审和验收等适用状态。已启动不等于已完成，本地通过不等于官方验收；不同源码版本、设备或范围的结果不能拼成同一版本的全量通过结论。
- 实验结论按需要链接源码版本、配置、环境、测试范围、原始结果和退出状态。当前摘要保留读者判断结论所需的信息，详细运行数据放在证据记录中。
- 结束时说明已完成、已取消或仍有遗留；遗留问题写明范围和去向。原任务结束后新增需求另记任务或阶段，不把已完成历史记录无限延长为待办清单。

## 更新与验证范围

- 变更代码、接口、配置、操作流程或任务状态时，检查直接受影响的当前说明、示例、索引和交付摘要。优先更新主要维护位置，再更新引用它的摘要，避免每轮新建一份重复状态报告。
- 文档修改后检查内部表述、相对路径、文件名、版本与数据的一致性。涉及表格、PPT 或其他交付格式时，核对本次采用版本中的对应信息；保留历史版本，不批量重写所有旧件。
- 仅修改文字、链接或排版且实现、配置、判据未变时，复用仍适用的验证证据，无须重新训练或重跑完整实机测试。命令、配置或行为说明改变时，按具体影响核查；确需执行的验证遵循本次授权和资源范围，不能验证的部分明确说明。
- 交付时简述修改了什么、核对了什么以及仍有何不确定。维护深度与任务规模相称，不为一次小改动自动增加计划、审计、报告等整套材料。
