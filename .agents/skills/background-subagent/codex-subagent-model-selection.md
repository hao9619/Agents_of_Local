# Codex subagent 模型选择

## 适用范围

适用于 Codex 的会话分工、辅助会话创建、子代理选型和交接。创建前先执行下述监管规则；本文件本身不要求使用子代理，实际执行仍受当前工具能力和会话约束限制。

用户明确指定的模型、推理强度及操作范围优先于本文默认建议。模型名称、支持的推理强度和参数组合以当前工具实际提供的能力为准。

## 主会话与辅助会话的监管

- 每个纳入管理的目录由用户创建并监管至少一个长期主会话。父目录主会话负责该层导航、共用规则和直属子项目协调；具体小项目的主会话负责深入实施。主会话身份由用户指定，安装规则或打开目录不会自动取得该身份。同一目录有多个主会话时，由用户明确各自分工及共同事项的最终负责人。
- 主会话在用户指定职责内拥有最高协调权；辅助会话不得自行改变其任务边界。该协调权不提高工具或文件权限，不凌驾于用户要求，也不自动接管其他目录主会话的工作。
- Codex 可以自行判断是否值得拆分临时任务，但创建任何辅助会话之前，须告知用户：目标与完成条件、工作目录、读写范围、预计时长和资源、建议由用户还是 Codex 监管，以及建议理由。等待用户选择；未答复不视为同意。
- 建议用户监管：长期推进、需要持续决策、跨项目协调或影响重要交付的会话。建议 Codex 监管：范围明确、周期短、结果可核验的临时任务。建议应结合实际任务，不能仅按任务名称决定。
- 用户选择自己监管时，主会话准备交接说明，由用户创建或接管会话；选择 Codex 监管时，主会话才通过可用工具创建、跟踪、验收和结束辅助会话。用户不采用拆分时，由主会话继续处理。
- 同一任务已经明确的监管选择在约定范围内持续有效，不重复询问普通执行步骤。新增辅助会话、改变监管者或扩大任务范围，须重新说明并取得对应选择；恢复原有执行者且范围不变无需重新决定。辅助会话不得自行再委派，确需拆分时返回主会话处理。
- 子目录按需安装规则不属于创建会话，不需要另行决定监管方式；安装仍须在本轮可写范围内。独立会话不会自动共享对话，读取和维护交接记录遵循[文档与目录规范](documentation.md)。

## 任务分级与模型选择

按任务需要的判断、背景依赖、结果可核验程度和出错后的影响选择模型，不按文字长度、文件数量或改动行数判断难度。

在工具允许独立指定模型时，采用以下默认规则：

| 任务类型 | 判断依据与例子 | 模型与推理强度 |
| --- | --- | --- |
| 机械任务 | 目标与规则明确、背景依赖少、判断需求低、结果容易核验；如提取指定日志字段、按固定格式整理已有结果、检查文件清单 | 可使用当前可用的最新 luna 模型，默认 `high` |
| 一般任务 | 需要理解、实现或综合判断；如代码分析、功能开发、论文方法理解、技术讲稿编写 | 优先使用当前可用的最新 sol 模型，默认 `high` |
| 复杂或影响面大的任务 | 涉及精度根因、实验设计、并发同步、跨模块修改或最终验收判定 | 至少按一般任务处理；根据具体难点选择当前可用的更强模型，或由主代理承担关键判断，并核查证据 |

- 模型标识如 `gpt-6.1-sol`、`gpt-6-luna` 仅为示例。同系列有多个可用型号时优先最新型号；不猜测未列出的模型名称。
- 文档任务不自动属于机械任务。解释方法、判断实验结论、编写连贯讲稿需要理解与判断；代码拆分和重构也不能仅因改动少就归为机械任务。
- 推理强度默认保留 `high`。仅对规则明确、容易核验的机械任务，可根据用户的速度或成本偏好，或已有使用效果，采用该模型支持的较低强度。评估效率时同时考虑返工、重复实验和设备等待成本。
- 默认偏好的模型不可用时，选择可用的合适模型或继承父会话。用户明确指定的型号不可用时说明情况，不静默替换；只有替代方案确需用户决定时才询问。

## 上下文继承与交接

先根据任务对前文的依赖选择继承方式，再在工具支持的范围内配置模型：

- `fork_turns: "none"`：任务能够通过明确说明和资料路径完整交代时使用。子代理不继承父会话历史；通过 `model`、`reasoning_effort` 指定独立配置。
- `fork_turns: "all"`：任务依赖大量前文决策、约束或调查过程，难以完整转述时使用。子代理继承父会话的模型与推理强度，不传入该模式不支持的覆盖参数。
- 工具支持其他继承方式时，按实际参数定义使用；不要为更换模型而省略完成任务所需的上下文。

无论是否继承历史，都要明确当前任务与边界。独立上下文的任务说明至少交代以下内容；无关项可以省略，已有文档可引用具体路径：

1. **目标与完成条件**：要解决的问题、交付内容和本轮做到什么程度。
2. **当前依据**：工作目录、适用的 AGENTS.md、相关文件及源码或实验版本。
3. **最新状态**：用户最新要求、已完成的验证、已排除的方案、未解决的问题和可复用证据。
4. **操作范围**：只读或可修改、允许修改的文件或目录，以及共享文件的负责人。
5. **资源使用范围**：是否允许下载、安装依赖、启动 GPU/NPU 作业或完整实验，以及已知的设备占用和资源限制。
6. **返回要求**：结论、证据位置、实际改动、验证范围与未解决问题；只读任务不要求生成文件。

派发前核对具体项目的当前状态，不能只转述可能过时的上层摘要。发生冲突时交代已核实事实和待核实部分；本次用户要求优先，历史授权不能自动沿用到其他项目。

主代理统一分配可修改文件和共享计算资源。共享接口、锁文件、配置与结果汇总文件应指定负责人，避免并发覆盖。子代理启动实验前核对已有结果和运行中任务；不得自行扩大实验范围、重复运行已满足本轮要求且版本仍适用的测试，或争用同一性能测试设备。已有明确授权无需重复询问。

## 升级处理与结果核查

- 子代理发现未预期的跨模块依赖、证据冲突或超出当前能力的关键判断时，返回已查明事实、具体难点和证据。主代理据此补充上下文、调整分工、更换模型或接手；不因单次普通报错机械升级，也不在缺乏新证据时反复重试。
- 遇到局部阻塞，继续完成范围内不依赖该阻塞的工作。不得通过猜测、放宽判据或扩大任务范围完成交差。
- 返回结论时区分观察、推断和未验证事项。实验或测试结果注明对应版本、环境、范围与证据位置；小样本流程跑通不能表述为全量结果复现。
- 主代理负责整合与关键核查，不能仅凭子代理说“已完成”就交付。不同版本、设备或测试范围的通过项不得拼成同一最终版本的全量通过结论。
- 优先检查已有证据和实际改动，按任务要求及具体风险验证。仅在必要检查缺失、结果冲突或改动影响已有结论时补测，不为确认子代理工作而默认重跑全部实验。
